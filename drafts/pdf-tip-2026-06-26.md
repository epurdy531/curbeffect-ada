Document Accessibility Tip of the Day

📃Topic: Font embedding and Unicode mapping📄

A PDF can look perfect on screen and still be unreadable to a screen reader if its fonts aren't carrying the right information underneath. Two things have to be true: the font has to be embedded in the file, and every glyph has to map back to a real Unicode character. When either is missing, assistive technology either guesses or reads nothing at all.

Embedding means the actual font program travels inside the PDF instead of relying on whatever font happens to be installed on the reader's machine. Without it, text can reflow, drop characters, or fall back to a substitute that no longer maps cleanly. In Acrobat Pro, open Document Properties and check the Fonts tab — anything that doesn't say "Embedded" or "Embedded Subset" is a risk. The cleaner fix is upstream: when you export from Word, choose the export path that embeds fonts (and avoid exotic or licensed display fonts that refuse to embed) so the problem never reaches the PDF.

Unicode mapping is the part people miss. A glyph can be embedded and still extract as garbage — the classic symptom is copying a line of text and pasting a string of boxes, question marks, or the wrong letters entirely. That's a broken ToUnicode mapping, and a screen reader will read exactly that garbage aloud. Test it the lazy way: select a paragraph, copy it, and paste it into a plain text editor. If what you get back is the real words, the mapping is sound. If it isn't, the font needs to be re-embedded or the text re-created, because no amount of tagging fixes characters that don't map to anything.

Watch especially for ligatures (fi, fl), "smart" quotes and dashes, bullet characters, and anything pasted from a design tool or scanned-then-OCR'd — those are where bad mappings hide.

🔍 Reference: for the exact normative wording, see PDF/UA clause 7.21 in your ISO 14289-1 copy.

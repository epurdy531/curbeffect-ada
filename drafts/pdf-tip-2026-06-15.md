Document Accessibility Tip of the Day

📃Topic: Form fields and the Form tag📄

A fillable PDF is only accessible if every interactive field is wired up so a screen reader can announce it correctly. Visual cues — a box, an underline, a label sitting next to the field — mean nothing to assistive technology unless the field itself carries the right semantics.

In Acrobat's Prepare Form tool, walk the document field by field and confirm that each one has a meaningful Name in the General tab and a Tooltip that reads the way you want the field announced. The Tooltip is what screen readers speak, so write it as the question the user is answering ("Date of birth" rather than "txt_dob_3"), and never leave it blank. Match the field type to what is being collected — text field, check box, radio button group, list box, dropdown — because the type determines how assistive technology lets the user interact with it. Radio buttons that belong together must share the same Name so they behave as a single group with mutually exclusive choices.

Then check the structure tree. Every form field needs to live inside a Form tag in the logical reading order, sitting where the user encounters it on the page. A field that exists as an annotation on the page but has no corresponding Form tag in the tree is invisible to a screen reader's reading mode. If you used Acrobat's auto-detect to add fields, open the Tags panel and confirm Form tags were created in the right places — auto-detection often misses fields or drops them at the wrong point in the reading order, and either has to be fixed by hand.

Finally, pair each field with its visible label. Putting the label text inside the same Form tag's structure, or marking the relationship clearly, is what lets the screen reader connect "First name" with the box the user is about to type into.

🔍 Reference: for the exact normative wording, see PDF/UA clause 7.18 in your ISO 14289-1 copy.
